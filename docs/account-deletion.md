# Account deletion implementation

`POST /v1/account/deletion` accepts an operation UUID, the current owner UUID, and a fresh Apple challenge/identity assertion plus Apple's authorization code. This route verifies Apple proof independently of an app bearer session so a lost response can be retried after the request revokes that session. The Apple subject must match the requested account. A mismatched account, expired nonce or reused sign-in challenge cannot initiate deletion.

An accepted request immediately disables the account, revokes all its sessions and cancels queued/running generation work. Community access checks reject inactive participants. The receipt explicitly distinguishes **pending** from **completed**. Pending is never presented as completed erasure. The client should retain the nonsecret owner/operation receipt after clearing local account storage so it can check progress using fresh Apple proof.

## Required production configuration

- `APPLE_SIGN_IN_TEAM_ID`: Apple Developer team identifier.
- `APPLE_SIGN_IN_KEY_ID`: identifier of a **Sign in with Apple** key.
- `APPLE_SIGN_IN_PRIVATE_KEY`: the key's PKCS#8 `.p8` contents. This is separate from an App Store Connect upload API key.
- Existing `APPLE_BUNDLE_ID`: the native app's client identifier.
- `ACCOUNT_DELETION_MAX_DAYS`: the operator's actual completion commitment, from 1 to 30 days. It has no invented default. Confirm the operational commitment before publishing a timeline or policy.

Missing revocation configuration or an uncommitted completion timeline is a public-launch readiness gap. Creating a durable request alone does not resolve it. No keys are generated by this implementation, and no production accounts are deleted by tests or deployment setup.

## Processing and recovery

The API processes confirmed requests at startup and every minute. A database advisory mutex prevents concurrent processors. The processing stages are durable: exchange the fresh authorization code, persist the encrypted refresh token, revoke the Apple grant, then erase supported account data in one database transaction. The exchanged Apple ID token is verified and must identify the same account before revocation. Codes and tokens never appear in receipts or logs; they are encrypted at rest using a key derived from the existing access signing secret. Keep that secret stable while requests are pending. If it rotates, unreadable credentials are discarded and the receipt requests fresh Apple proof instead of leaving an unrecoverable refresh token.

Apple authorization codes expire quickly. A stale unexchanged code is discarded and the receipt requests reauthentication. Repeating the original operation with fresh same-owner Apple proof replaces an unexchanged code while preserving a reusable refresh token or successful revocation. A definitively rejected refresh token can also be replaced through fresh proof; transient failures retain it. All credential and error updates compare the previously read ciphertext, kind and exact database timestamps, so an old worker snapshot cannot erase newer authorization. Invalid key configuration, unsupported legacy schema and other failures remain pending with sanitized error codes. The next worker pass retries eligible requests; blocked old requests cannot starve new ones.

For an explicit operational pass against a reviewed database:

```
CONFIRM_ACCOUNT_DELETION_PROCESSING=yes node --import=tsx scripts/process-account-deletions.mjs
```

This command processes existing confirmed requests; it cannot initiate deletion. Operators must inspect pending requests and resolve configuration or schema failures. Apple credentials and the committed timeline must be configured and an end-to-end completion verified before claiming this is operational for public release.

## Erasure boundaries

Completion removes the user's current profile, library, review history, sync changes, receipts, generation data, quota records, import manifests, legacy archives, sessions, friendships, invitations, participant share snapshots/mappings, blocks and reports that contain their identity/content. Known legacy `public` tables are erased only after matching both their UUID and verified Apple identity. Unsupported columns, unknown inbound foreign keys, conflicting identities or cross-owner legacy references leave the request pending for explicit review; no broad `CASCADE` is used.

Recipient-owned independent copies and their own review history remain, as described by deck sharing. Their attribution/share records are removed. There is no transitive provenance for text that people independently copied or shared again; do not promise deletion of other users' independent libraries.

A minimal receipt retains the old owner UUID, hashed Apple subject, request/status timestamps and operational state after erasure. It contains no name, email, photo, card text or plaintext Apple credential. It prevents old imports from restoring the erased UUID. Pending requests block sign-in; after completion, a new Apple sign-in can create a fresh empty account with a new UUID. Old legacy identities covered by a deletion receipt are never reused.

Local SQLite, widget and original native recovery stores are a separate client erasure responsibility. The public policy must describe actual storage and backup retention rather than promise that database deletion erases previously exported personal files.
