# Optional app analytics and session replay

Recollect uses PostHog for optional screen-usage analytics and masked native session replay on iOS. Android and web collection remain disabled. The current Android bridge hides native status-query errors, so this rollout cannot reliably confirm recording stopped there before reusing an identity. Collection starts only after the signed-in user explicitly enables **You → App analytics & replay** for that account on that device. Leaving the setting off does not limit the learning app. AI sharing permission and Marketplace practice-contribution permission remain separate choices.

## Collection boundaries

- Identify consenting sessions using only the internal account UUID. Do not add email, name, Apple identifiers/assertions, profile details, learning content, prompts, invite codes, report narratives, or purchase proofs to events or person properties.
- Send screen route templates, such as `/decks/[id]`, without resolved IDs, search parameters, friend names, or invitation values. Do not send raw navigation state or incoming URLs.
- Keep global text, input, image, and sensitive-view masking enabled. Text outside input fields includes card questions/answers, deck names, profile email, friend names, and deletion references. Profile and deck photos must stay masked.
- Keep touch autocapture, network request capture, console-log capture, and automatic error capture disabled. JavaScript analytics events disable GeoIP enrichment; verify the project-level GeoIP controls and native replay metadata before making the same claim for native snapshots. Accessibility labels contain deck/card content in several screens; enabling autocapture requires a separate review of those labels and properties.
- Stop recording and reset the active identity when permission is withdrawn, the account signs out or changes, or account deletion is busy or pending. Exclude sign-in, profile, token/purchase, and account-deletion/recovery screens from replay, including native Apple authentication and photo-selection flows launched there. Other states without an eligible signed-in account must not record.
- Default development collection to off. Any explicit development enablement must use test accounts and a suitable project; never assume a development build is excluded solely because its app version differs.

Masking is a configuration that needs verification in the installed app. Do not unmask views to improve replay usefulness without a fresh content and privacy review. PostHog can receive technical app/device metadata and the requests needed to ingest events; an internal UUID is an account-linked identifier, not an anonymous identity.

## Configuration

| Variable | Value to supply | Handling |
| --- | --- | --- |
| `EXPO_PUBLIC_POSTHOG_PROJECT_TOKEN` | The intended PostHog project's client ingestion token | Public client configuration, embedded in the app bundle. Never substitute a personal API key. |
| `EXPO_PUBLIC_POSTHOG_HOST` | The ingestion host for that same project | Use the project's verified HTTPS host, including any approved proxy. Do not infer the host or processing region from another project. |

Keep actual values out of this document and issue/review screenshots. Configure both values together. Verify that missing or invalid configuration leaves analytics unavailable and collection off; it must not prevent app startup, sign-in, offline learning, or account deletion.

The repository's automated native release builds the EAS `testflight` profile using the **preview** environment and `testflight` update channel. Set GitHub Actions variables with these exact names in the repository's `main` environment. The release workflow validates both values and writes them to EAS `preview` before either a native build or a compatible OTA; it also explicitly disables development capture. Values configured only under EAS `production` do not configure that TestFlight pipeline. Keep build and update values consistent so a later OTA does not silently switch hosts/projects or disable the consented feature.

The initial integration adds native modules. Release it through a `feature/*` pull request and the automated native build/TestFlight workflow. `enhancement/*` requests an OTA; `codex/*` and `feat/*` are not valid native release branches under the current release policy. Do not manually build, upload, submit, or deploy as a fallback. Fix CI/CD when delivery fails. CI writes release/native versions; do not invent a version or bypass fingerprint compatibility checks.

## Verify before public release

Use a real supported iOS device with the exact CI-built native candidate. Synthetic content must be distinctive enough to search for accidental disclosure; use fictional profiles, emails, deck/card text, prompts, photos, friend names, invite codes, and report text. Keep real credentials and purchase proofs out of test artifacts.

1. **Before permission:** launch, sign in, navigate, type into fields, and background/resume the app while the choice remains off. Inspect ingestion/network evidence and the PostHog project to confirm no analytics events, identity association, or replay from this install. Repeat after relaunch. The consent panel itself must not trigger collection before acceptance.
2. **After permission:** opt in and exercise Today, decks/categories, card editing, generation/draft review, card practice and reading sheets, insights, Friends/invitations/sharing, Marketplace/reporting, and native overlays that the SDK can observe. Also open the excluded profile/photo, token/purchase, sign-in, and deletion/recovery flows to verify replay stops before their contents or native overlays are captured. Verify at least one completed replay arrives in the intended project and plays correctly. A successful initialization or one screen event is not proof of working replay.
3. **Inspect the data:** check event and person properties, screen names, replay frames, and available replay metadata. Confirm that only the account UUID identifies the user, routes are templates, text/input/images remain masked, and the distinctive synthetic values do not appear. Check accessibility-derived properties as well as visible frames. Confirm that no console logs, network contents, automatic error events, or automatic touch events were collected. Review technical device/app and request metadata rather than assuming it is absent.
4. **Exercise transitions:** withdraw permission, sign out, switch accounts, background/resume, force-close/reopen, go offline/online, start deletion, cancel or fail fresh Apple confirmation, enter pending deletion/recovery, and complete deletion where test infrastructure permits. Verify recording stops during ineligible states, one account never inherits another's permission or identity, queued work does not cross the boundary, and opting out remains effective after relaunch. Verify login and recovery screens stay excluded.
5. **Test unavailable configuration and service failures:** the app must remain usable with missing configuration, no network, or an unreachable PostHog host. Verify consent persists without enabling collection for another account/device. Development builds remain off unless explicitly enabled.
6. **Record evidence:** retain the candidate version/build, commit, runtime, CI run, test device/OS, relevant configuration names, test date, and restricted links to the inspected test events/replays. Do not copy replay payloads or sensitive identifiers into public PRs, logs, or routine release notifications.

Also complete the normal repository checks, Expo bundle/prebuild validation, and native configuration/fingerprint checks. Source tests and configuration checks complement the device inspection; they do not replace it. A CI upload to Apple does not establish Apple processing, review approval, or public availability.

## Privacy and operator release gates

- Deploy the matching public privacy policy through the website's automatic CI/CD path before enabling collection. Verify the live page describes optional collection, the account/device choice, masking, PostHog, and the limits of withdrawal/deletion. Preserve the distinction between optional analytics and required service diagnostics.
- Review App Store Connect App Privacy against the inspected data flow and Apple's current definitions before public release. Include the optional collection path. Consider usage/product-interaction information, account identifiers, device/app metadata, and any other observed SDK data. Confirm linkage and purposes; the account UUID links events/replays to an account. Determine tracking from actual uses and sharing, not the presence or absence of advertising or the SDK name. Verify SDK privacy manifests in the generated app.
- Confirm project membership, replay access permissions, the intended host/project, actual event/replay retention settings, and GeoIP enrichment controls for native replay requests. Record these in restricted operational records. Do not state a retention duration, processing region, or immediate erasure guarantee without verifying the provider configuration and process.
- Account deletion stops local collection and identity association. It does **not** automatically erase previously ingested PostHog events, person records, or replays. Establish an operator process for requests through Recollect support, including locating records by the relevant account identifier, checking the provider's deletion controls and their scope, and recording completion accurately. Do not promise provider erasure based only on the account database's deletion status.
- Recheck masking and capture boundaries after SDK upgrades, native UI changes, new content surfaces, routing changes, or provider remote-setting changes. Do not enable broader capture remotely without reviewing the app behavior and disclosures.

References for the release review: [Apple App Privacy details](https://developer.apple.com/app-store/app-privacy-details/), [App Privacy in App Store Connect](https://developer.apple.com/help/app-store-connect/manage-app-information/manage-app-privacy), and [PostHog privacy policy](https://posthog.com/privacy). Use the provider's current documentation and project settings when carrying out the review; these links are not evidence that the project's settings have been verified.
